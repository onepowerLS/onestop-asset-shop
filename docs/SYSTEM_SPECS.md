# 1PWR AM — System Specifications

Living document. Update whenever a behavior rule, policy, or cross-cutting convention is added or changed.

## 1. What's New popup primer at login

**Purpose.** When a user logs in, surface a multi-page modal that explains feature updates shipped since their last visit. This closes the loop between engineering changes and field users (Metro, Thabo, etc.) who only see the tool, not the commits.

### Triggering rule

- On every page load (for logged-in users), the client calls `GET /api/whats-new/unseen.php`.
- If the response has `entries: []`, no popup is shown — silent load.
- If the response has one or more entries, a modal opens automatically on the first page load after they become available.
- The modal is also reachable manually from `Help → What's new` and the sidebar `What's new` link.

### Modal behavior

- Multi-page: one page per entry, with Next / Back / Skip / Finish controls.
- The user can close/cancel at any time. Closing (any way) marks all currently-seen entries as dismissed for that user, so the popup does not reappear next login.
- A "Don't show again until next batch" link is equivalent to dismiss.
- The modal is dismissible with ESC, the X button, and a "Maybe later" button.

### Per-user state

- Dismissals are stored in Firestore `am_core_whats_new_dismissals`, keyed by `user_id + entry_id`.
- Dismissing marks **all entries that were eligible at the time of dismissal** as seen — the client passes the list of entry IDs it was shown, the server records them all.
- A user can re-open the archive from `Help → What's new` and revisit any entry.

### Entry lifecycle (admin)

- Admins create entries at `Admin → What's New` (`web/admin/whats-new.php`).
- Each entry has: `title`, `summary`, `details` (HTML/markdown-safe text), `category` (feature / improvement / fix / reconfigure), `icon` (FontAwesome), `released_at`, `active` flag, optional `deep_link`.
- Entries are ordered by `released_at` descending in the popup.
- Deactivating an entry removes it from the popup and the public archive but keeps the Firestore document for audit.

### When to add an entry

**Rule of thumb.** Any commit (or set of commits) that meets the test of constituting a **novel feature** or a **reconfigured feature** must produce a `am_core_whats_new` entry and trigger the popup for users who haven't seen it.

Examples that **do** require an entry:
- A new workflow (e.g. bulk ready board allocation, Assemble / produce).
- A new field on an existing form (e.g. Department on Allocated items).
- A changed behavior with user-visible impact (e.g. search-catalog-first on Add Item, location alias dedupe).
- A new admin tool or report.

Examples that **do not** require an entry:
- Pure refactors with no UI/UX change.
- Linter/syntax fixes.
- Schema docs that don't change behavior.
- Performance optimizations invisible to the user.

### Archive

- Historical entries remain browsable at `web/whats-new.php` (sidebar `What's new`) even after the user has dismissed them.
- This is the companion to `Help` and the interactive `Tutorial` — together they form the user-education surface.

### Firestore schema

See `docs/FIRESTORE_SCHEMA.md` for `am_core_whats_new` and `am_core_whats_new_dismissals`.

## 2. Mutation logging

Every create/update/delete on `am_core_*` collections goes through `am_firestore_*_document()` helpers in `web/config/firestore.php`, which call `am_mutation_log_record()` to write to `am_core_mutation_logs`. See `docs/FIRESTORE_SCHEMA.md` for the log shape.

## 3. Country scope

Users are scoped to one or more countries via session (`am_ensure_country_scope_from_session`). All list views and mutations enforce this. Admins can access all countries.

## 4. Item class taxonomy

Fixed Asset, Material, Consumable, Inventory. Controlled by `pr_master_categories`. Adding categories is done via `Admin → Manage Categories` (or the seed buttons there). See `docs/SOP-ITEM-CLASSIFICATION.md`.

## 5. Asset tag uniqueness

Generated by `am_generate_unique_asset_tag()`. Tags are of the form `1PWR-<CLASS>-<COUNTRY>-<NNNNNN>`. Add and Edit flows block collisions. Duplicate Review (`Data quality → Duplicate review`) catches legacy collisions and offers merge with 30-day purgatory.

## 6. Location canonicalization

Inventory rows use canonical `location_code` (e.g. `LSO-HQ`). Legacy alias keys (`site1`, `HQ`) are resolved via `am_canonical_location_code()` and merged on read in `am_inventory_dedupe_all_levels()` so duplicate rows are not summed.

### Canonical source of locations (country-aware)

The **PR portal** (`pr.1pwrafrica.com`) is the canonical system for the country-aware list of sites. AM never authors sites — it reads them live from Firestore on every page load via `am_get_pr_sites()` (in `web/config/firestore.php`), which consults three collections in this order, deduping by `code | country`:

1. `am_reference_sites` — PR fanout cache (preferred when present). Written by PR via `web/api/sync/site-ingest.php`.
2. `sites` — Lesotho field sites (Lesotho canonical, public read).
3. `referenceData_sites` — multi-org sites for Benin, Zambia, etc.

Each site is normalized to a record with `country_code` (ISO-3, derived from `organizationId` → `1pwr_lesotho=LSO`, `1pwr_benin=BEN`, `1pwr_zambia=ZMB`), `location_code` (`<CCO>-<CODE>`, e.g. `LSO-HQ`), `location_name`, `region`, `active`, and lat/long.

To add, rename, move, or deactivate a site: do it in the PR portal. AM picks up the change on next page load (no AM-side seed/migration step). The Admin → Locations page (`web/admin/locations.php`) is a read-only viewer that shows what AM currently sees and is the first place to look when a site dropdown is empty.

### Loadout manifest destination

`destination_site_id` is required for every loadout manifest save except `Cancelled` (including `Draft`). Validation lives in `web/loadout/edit.php` and the form field is marked required. When the site dropdown is empty because PR portal sync returned no sites, the form shows an inline error linking to Admin → Locations.

## 7. Inventory read API (machine consumers)

Read-only `/api/v1/*` endpoints (Brief 01) expose stock position, allocations, movements, parts and loadouts to ugridpredict / Nexus / reporting.

- Auth: existing `X-API-Key` scheme (`AM_API_KEY_UGRIDPREDICT`, `AM_API_KEY_NEXUS`, `AM_API_KEY_REPORTING`, plus legacy mutation/loadout keys). Resolves to `am_firestore_admin_access_token()`. 60 req/min per consumer. Every call is logged (`consumer`, endpoint, status, duration_ms).
- `qty_available` is computed server-side as `qty_on_hand - qty_allocated`. Consumers must not derive it.
- Stock is held **per location**. A location is the store; `site_id` and `store_id` are both the canonical `location_code` from `am_reference_sites`.
- `/api/mutations` is a **record-edit audit log**, not a stock ledger. Movements live in `am_core_inventory_movements` and are also projected from `am_core_transactions` so history is readable immediately.
- `ugp_part_id` on `am_core_assets` is the join to UGP BOM lines. Do not auto-fuzzy-match. `GET /api/v1/parts?unmapped=true` is the data-quality worklist.
- Units are `am_core_assets.unit_of_measure` (`EA`, `M`, `KG`, `L`, `BOX`, `ROLL`, `SET`). Conductor is `M`.
